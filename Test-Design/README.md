# 🧪 Test Design

Раздел содержит практические примеры применения **техник тест-дизайна** при проектировании тестовых сценариев.

Цель — показать умение анализировать требования, выбирать подходящую технику тестирования, сокращать количество избыточных проверок и обеспечивать достаточное тестовое покрытие.

# 1. Эквивалентное разбиение

**Equivalence Partitioning** используется для разделения входных данных на группы, внутри которых система должна обрабатывать значения одинаковым образом.

В практическом примере поле **«Возраст»** принимает значения от `18` до `65` лет.

Выделены три класса:

- меньше 18 — невалидный;
- 18–65 — валидный;
- больше 65 — невалидный.

Это позволяет вместо проверки каждого возможного значения выбрать представителей каждого класса.

---

# 2. Анализ граничных значений

**Boundary Value Analysis** используется для проверки значений непосредственно на границах допустимого диапазона и рядом с ними.

Для диапазона `18–65` проверяются:

```text
17, 18, 19
64, 65, 66
```

Такой подход помогает обнаруживать типичные ошибки в условиях сравнения, например использование `>` вместо `>=`.

---

# 3. Позитивные и негативные сценарии

На примере формы регистрации представлены:

### ✅ Позитивные проверки

Проверяют работу системы с корректными пользовательскими данными.

### ❌ Негативные проверки

Проверяют:

- пустые обязательные поля;
- неправильный формат Email;
- отсутствие домена;
- слишком короткий пароль;
- комбинации нескольких некорректных условий.

---

# 4. Таблица принятия решений

**Decision Table** используется для проверки функциональности, результат которой зависит от комбинации нескольких условий.

В примере рассматривается авторизация пользователя.

Условия:

- Email зарегистрирован;
- пароль правильный.

Для двух условий рассматриваются четыре возможные комбинации и определяется ожидаемое действие системы для каждой из них.

Это позволяет системно проверить бизнес-логику и не пропустить комбинацию условий.

---

# 5. Pairwise Testing

**Pairwise Testing** используется для оптимизации большого количества комбинаций параметров.

В практическом примере используются:

**Браузеры:**

- Chrome;
- Firefox;
- Safari.

**Операционные системы:**

- Windows;
- macOS;
- Android.

**Языки:**

- Русский;
- Английский.

Полный набор содержит:

```text
3 × 3 × 2 = 18 комбинаций
```

Pairwise-подход позволяет сформировать сокращённый набор проверок с покрытием взаимодействия пар параметров.

---

# 6. Диаграмма переходов состояний

**State Transition Testing** применяется, когда поведение системы зависит от текущего состояния объекта.

В качестве примера используется жизненный цикл заказа:

```text
New
 │
 ├── Оплата ──► Paid ──► Delivered
 │                │
 │                └── Отмена ──► Cancelled
 │
 └── Отмена ──► Cancelled
```

Проверяются как допустимые, так и запрещённые переходы между состояниями.

Например:

- `New → Paid` — допустимо;
- `Paid → Delivered` — допустимо;
- `Delivered → Cancelled` — недопустимо;
- `Cancelled → Paid` — недопустимо.

---

# 7. Предугадывание ошибок

**Error Guessing** основан на опыте тестировщика и предположении о потенциально проблемных местах системы.

Для формы регистрации рассматриваются сценарии:

- пробелы в Email;
- Email в верхнем регистре;
- повторное нажатие кнопки;
- повторная регистрация существующего Email;
- очень длинные значения;
- нестандартные символы;
- обновление страницы после отправки;
- потеря сетевого соединения;
- потенциально опасный пользовательский ввод.

Эта техника дополняет формальные методы тест-дизайна нестандартными проверками.

---

# 8. Матрица трассируемости

**Traceability Matrix** используется для связи требований с тестовыми сценариями.

В практическом примере требования формы регистрации связаны с соответствующими Test Case ID.

Матрица позволяет определить:

- какие тесты покрывают конкретное требование;
- существуют ли требования без тестов;
- есть ли тесты без связи с требованиями;
- насколько полно требования покрыты проверками.

В примере:

```text
Всего требований: 6
Покрыто требованиями тестами: 6
Покрытие: 100%
```
